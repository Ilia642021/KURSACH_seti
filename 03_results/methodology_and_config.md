# Методология и конфигурация сценариев моделирования

В данном документе описывается техническая реализация четырех сценариев (A, B, C, D) для курсового проекта (Вариант 8), а также способы получения результатов.

## 1. Общие настройки (General)
Все сценарии базируются на общей конфигурации в [omnetpp.ini](file:///home/dev/6_sem/KURSACH_seti/02_model/kursach_model/omnetpp.ini):
- **Стек**: OMNeT++ 6.0.3, INET 4.5.
- **Протокол маршрутизации**: OSPFv2 с поддержкой динамического перестроения.
- **Модель трафика**: Использование `PingApp` для измерения RTT (Round Trip Time).
- **Размер сообщения**: 800 байт (согласно заданию).
- **Время замера**: Начало замеров на 30-й секунде (после полной сходимости OSPF при старте).

---

## 2. Сценарий A: Базовый режим (Base)
**Цель**: Оценить работу сети через основной канал связи с провайдером.

- **Конфигурация**:
    - `numHqHosts = 30` (30 рабочих мест в центральном офисе).
    - **Особенность**: Резервный канал (интерфейс `ppp[3]` на маршрутизаторе `core`) принудительно отключается на 1-й секунде симуляции.
- **Код настройки**:
  ```ini
  [Config A_Base]
  *.scenarioManager.script = xml("<at t='1s'><shutdown module='core.ppp[3]'/></at>")
  ```
- **Получение результатов**: Значения RTT берутся из файла `A_Base-0.sca` (среднее значение `rtt:mean`).

---

## 3. Сценарий B: Резерв включен (Reserve Enabled)
**Цель**: Проверить работу сети при наличии двух исправных каналов.

- **Конфигурация**:
    - `numHqHosts = 30`.
    - Оба канала (основной 30 Мбит/с и резервный 10 Мбит/с) активны.
- **Логика**: OSPF автоматически выбирает основной канал как приоритетный из-за более высокой пропускной способности (меньшая стоимость метрики).
- **Получение результатов**: Анализ `B_ReserveEnabled-0.sca` показывает идентичные с A результаты, что подтверждает корректность выбора пути OSPF.

---

## 4. Сценарий C: Отказ основного канала (Failure)
**Цель**: Доказать отказоустойчивость и измерить время сходимости.

- **Конфигурация**:
    - `numHqHosts = 30`.
    - На 10-й секунде происходит программное отключение основного канала (`core.ppp[2]`).
- **Код настройки**:
  ```ini
  [Config C_FailurePrimary]
  *.scenarioManager.script = xml("<at t='10s'><shutdown module='core.ppp[2]'/></at>")
  ```
- **Ключевые доработки для успеха**:
    1. **Fast OSPF**: В [ASConfig.xml](file:///home/dev/6_sem/KURSACH_seti/02_model/kursach_model/ASConfig.xml) установлены `helloInterval="1s"` и `routerDeadInterval="4s"`.
    2. **ISP OSPF**: На узле `isp` включен OSPF (`*.isp.hasOspf = true`), чтобы провайдер знал о перестроении маршрута.
- **Получение результатов**:
    - Время сходимости вычисляется по логам (`simulation.log`) как разница между событием `shutdown` и событием `OSPF Neighbor State Change: Full` на резервном интерфейсе.
    - RTT после отказа замеряется после 30-й секунды.

## 5. Сценарий D: Масштабирование (Scale Up)
**Цель**: Оценить влияние увеличения количества узлов на задержки.

- **Конфигурация**:
    - `numHqHosts = 43` (30 базовых + 13 дополнительных согласно заданию).
    - Оба канала активны.
- **Получение результатов**: Сравнение `D_ScaleUp-0.sca` с `B_ReserveEnabled-0.sca`. Незначительное увеличение задержки (на доли миллисекунд) подтверждает масштабируемость сети.

---

## 6. Инструментарий для извлечения данных
Для получения финальных цифр использовались следующие методы:
1. **Scalar Analysis**: Чтение средних значений из `.sca` файлов в `03_results/omnetpp/`.
2. **Log Grepping**: Поиск конкретных событий в выводе симуляции:
   ```bash
   grep "Changing neighborhood state" simulation.log  # Для замера сходимости
   grep "reply received" simulation.log               # Для проверки прохождения трафика
   ```
3. **Evidence Guide**: Детальные ссылки на строки логов собраны в [evidence_guide.md](file:///home/dev/6_sem/KURSACH_seti/03_results/evidence_guide.md).
